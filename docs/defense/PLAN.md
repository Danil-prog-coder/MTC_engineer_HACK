## 0. Принципы

1. **Тезис**: «я понимаю, что построил, почему, и где предел». Сами называем слабые места — это даёт баллы по критерию «ограничения», а вопрос жюри «а что если узел упадёт?» превращается в заготовленный ответ.
2. **Ничего не заявляем сверх README.** В README уже есть честные разделы «Известные ограничения» и «Сеть: нюансы». Любое расхождение слайда с README жюри найдёт.
3. **Бюджет слов.** Комфортный темп — 130–140 слов/мин. На 4 минуты ≈ 540 слов. Сценарий ниже уложен в 540–560; прогони с секундомером и режь, а не ускоряйся.
4. **Слайдов 5 основных + запасные** (запасные в конце PDF, на экран не выводим, но открываем при вопросе).
5. **Слайд — опора, а не текст.** Максимум 5–6 коротких строк или одна схема.

## 3. Слайды 2–4. Представление решения (2:00, ~265 слов)

### Слайд 2. Какую архитектуру выбрали и почему (0:50)

**На слайде**: схема из README (упростить до 5 блоков) и подпись:
`make deploy` → kubeadm 1.36 (1 узел, Calico) → Envoy Gateway (Gateway API) → Angie ×2 версии → Prometheus/Grafana + Fluentd→VictoriaLogs

**Ответ по сути (для речи и для вопросов)**
- **Что**: чистая Ubuntu 24.04 → одна команда `make deploy` (Ansible + Helm + Kustomize) → рабочий кластер kubeadm, приложение, доступ через Gateway API, метрики и логи. `make verify` сам доказывает работоспособность (17 проверок, отчёт с реальными ответами).
- **Путь запроса**: клиент → NodePort 30080/30443 → Envoy Proxy (×2) → `HTTPRoute` → Service → Angie. Envoy создаёт/сохраняет `X-Request-Id`, Angie пишет его в лог и возвращает в ответе.
- **Метрики**: Prometheus тянет Angie (:9113), Envoy (:19001), Fluentd (:24231) и кластер (kube-prometheus-stack). Дашборды Grafana — из git.
- **Логи**: stdout → `/var/log/containers` → Fluentd (DaemonSet, дисковый буфер) → VictoriaLogs. По `request_id` одним запросом находится и запись Gateway, и запись приложения.
- **Почему kubeadm, а не kind/k3s**: цель кейса — «настоящий» кластер; kubeadm показывает все слои (CRI, CNI, CSR kubelet, control-plane).
- **Почему такая «слоёность»**: Ansible готовит хост и кластер, Helm ставит версионированные чарты, Kustomize описывает наши манифесты, Make — единая точка входа. Каждый инструмент делает то, в чём силён, и всё идемпотентно.

**Речь (~120 слов)**
> «Решение — это воспроизводимая платформа: одна команда `make deploy` на чистой Ubuntu поднимает кластер kubeadm с Calico, Envoy Gateway, приложение на Angie, Prometheus с Grafana и логи через Fluentd в VictoriaLogs. Трафик идёт так: клиент попадает на Envoy, тот по HTTPRoute направляет в сервис Angie. Метрики Prometheus собирает с Envoy, Angie и кластера; логи уходят во VictoriaLogs. Ключевая деталь: сквозной request_id — Envoy создаёт его, Angie пишет в лог и возвращает клиенту, поэтому по одному идентификатору находятся записи и шлюза, и приложения. Выбрал kubeadm, потому что задача — настоящий кластер, а не имитация, а команда `make verify` сама доказывает, что всё работает.»

### Слайд 3. Три ключевых технических решения (0:50)

| # | Решение | Почему | Альтернатива и почему нет |
|---|---|---|---|
| 1 | **Gateway API + Envoy Gateway**, роли по namespace: Gateway в `gateway-system`, маршруты в `hello`, допуск через `allowedRoutes` по метке | Ingress — прошлое поколение: аннотации вместо типизированных ресурсов, нет разделения ролей. Gateway API даёт `HTTPRoute` с весами (90/10), маршрутизацию по заголовку, редирект, политики (`BackendTrafficPolicy`) — всё декларативно | NGINX Gateway Fabric, Cilium: Envoy Gateway — эталонная реализация со встроенными метриками и политиками. Ingress-NGINX — [ПРОВЕРЬ формулировку: проект объявлен к выводу из поддержки] |
| 2 | **Идемпотентность как требование**: Ansible + Helm с зафиксированными версиями + server-side apply; `versions.yaml` — единственный источник версий; `make idempotency-check` требует `changed=0` | Повторный запуск безопасен и показывает, что руками ничего не правили (нет дрейфа). | 3 | **Evidence-as-Code**: `make verify` — 17 автопроверок + сквозной `request_id` + CI | Проверяемость вместо «поверьте на слово»: отчёт содержит реальные ответы curl, PromQL и логов | Ручной чек-лист — не воспроизводим, не ловит регрессии |

Дополнительно «безопасность по умолчанию» (одной строкой): PSA `restricted` в `hello`, default-deny NetworkPolicy, non-root, read-only FS, TLS через cert-manager.

**Речь (~85 слов)**
> «Три ключевых решения. Первое — Gateway API с Envoy Gateway: типизированные маршруты, разделение ролей по namespace, весовое деление трафика 90/10 и политики без аннотаций; это то, что пришло на смену Ingress. Второе — идемпотентность: версии зафиксированы в одном файле, нет тега latest, а отдельная проверка требует, чтобы второй запуск ничего не менял. Третье — проверяемость: `make verify` формирует отчёт с реальными ответами сервиса, метриками и логами, а CI проверяет манифесты.»

### Слайд 4. Сложности и границы (0:20)

**Сложности → как решили** (все из истории репозитория):
1. Сеть с блокировками (типично для VPS в РФ): образы и пакеты не скачивались → автоопределение недоступных источников и профиль зеркал, загрузки с повторами и докачкой, кэш артефактов; повторный деплой после `destroy` ≈ 6 мин.
2. CRD Envoy Gateway: Secret релиза Helm превышал 1 МиБ → `helm template` + server-side apply.
3. Упавший `kubeadm init` оставлял грязное состояние → автоматический `kubeadm reset`, чтобы повторный запуск начинался с чистого листа.
(Если останется время/вопрос: Fluentd терял не-JSON error-логи → маршрут `@ERROR`.)

**Границы (честно, одной строкой)**: один узел, NodePort вместо 80/443, самоподписанный CA, хранилища без бэкапов — всё это осознанно и описано в README; закрываем в кейсе.

**Речь (~60 слов)**
> «Самая большая сложность — сеть: на российских ВМ часть реестров недоступна, поэтому деплой сам определяет это и подключает зеркала, а загрузки идут с повторами. Ещё CRD Envoy превышали лимит секрета Helm — перешёл на `helm template` и server-side apply. Границы я знаю: один узел, NodePort, самоподписанный сертификат — они описаны в README и разобраны дальше в кейсе.»

## 5. Слайд 6. Ситуационный кейс (1:00, ~135 слов)

Условие: 2 недели, 3 крупных изменения, потом 24/7.

**Логика выбора**: сначала «не лежать» (SPOF), потом «узнать, что лежим» (наблюдаемость, которая сама не умирает вместе с кластером), потом «не быть взломанным и не зависеть от чужих зеркал» (безопасность и цепочка поставки). Всё остальное либо дороже, либо менее критично для старта.

| # | Изменение | Какой риск снижает | Почему выше остальных | |
|---|---|---|---|---|
| 1 | **Отказоустойчивость и нормальный вход**: 3 control-plane + ≥2 worker, VIP/LB (kube-vip или MetalLB / облачный LB) на 80/443, публичный домен + Let's Encrypt, anti-affinity и PDB; + cron-снапшоты etcd | Сейчас один узел = любая поломка узла, обновление или диска = полный простой; клиенты не ходят на :30080 и не доверяют самоподписанному CA | Требование 24/7 несовместимо с единой точкой отказа; остальное бессмысленно, если сервис недоступен целиком | |
| 2 | **Алертинг и дежурство**: Alertmanager → Telegram/почта/PagerDuty, SLO-алерты (burn-rate по доступности и 5xx), **внешняя blackbox-проверка** вне кластера, Prometheus/логи на сетевом/реплицируемом диске с retention, runbook на каждый алерт | Метрики и алерты есть, но **никто не получает уведомление**; мониторинг внутри кластера не увидит падение самого кластера; history пропадёт вместе с диском узла | Без этого простой обнаружит клиент. Это самый дешёвый способ сократить MTTD | |
| 3 | **Безопасность и цепочка поставки**: Grafana/Prometheus за аутентификацией (или только через VPN), убрать `/__error_demo`, закрыть метрики control-plane файрволом, secrets через SOPS/External Secrets, собственный registry/зеркало с проверкой образов (digest/подпись) вместо неофициальных зеркал | Публикация в интернет резко повышает поверхность атаки; неофициальные зеркала без проверки подписи — риск подмены образов | Утечка или компрометация хуже простоя, но эта работа требует решений №1 (публичный вход), поэтому идёт третьей | |

**Сознательно откладываем на следующий этап**: GitOps (Argo CD) и мульти-окружения; автомасштабирование (HPA/KEDA) и нагрузочные тесты; Velero и полноценный DR-тест (в п.1 только снапшоты etcd); процесс обновления Kubernetes без простоя (регламент + staging); глобальный rate limit; бизнес-метрики/SLO-отчёты; сертификация/аудит.

**Почему не взял «бэкапы/DR» отдельным пунктом**: приложение stateless, вся платформа воспроизводится из кода за ~6–15 мин (проверено повторным `destroy → deploy`), поэтому главная потеря при аварии — история метрик/логов, а не бизнес-данные. Минимум (снапшоты etcd) входит в п.1, полный DR — следующий этап.

**Речь (~140 слов)**
> «Чтобы выйти в production за две недели, расставил приоритеты по принципу: не упасть, узнать об этом, не быть уязвимым. Первое — отказоустойчивость: сейчас один узел и NodePort, это единая точка отказа. Поэтому три control-plane, несколько worker-узлов, балансировщик с VIP на 80 и 443 и публичный сертификат. Второе — алертинг: алерты есть, но получателя нет, и мониторинг внутри кластера не заметит падение самого кластера. Добавляю доставку алертов, SLO и внешнюю проверку снаружи. Третье — безопасность: закрыть Grafana и Prometheus аутентификацией, убрать демо-эндпоинт, заменить сторонние зеркала на собственный registry. На потом оставляю GitOps, автомасштабирование, полноценный DR и регламент обновления Kubernetes: это важно, но не блокирует запуск.»

## 6. Подготовка к вопросам (4 минуты — это половина времени, баллы в основном тут)

Короткие ответы (15–25 секунд). Везде: **факт → причина → ограничение**.

**Архитектура и выбор**
1. *Почему Gateway API, а не Ingress?* — Типизированная модель (Gateway/HTTPRoute), разделение ролей, веса и заголовки без аннотаций, политики; Ingress заморожен в развитии.
2. *Почему Envoy Gateway?* — Эталонная реализация, метрики и политики Envoy из коробки, активно поддерживается. Альтернативы (NGINX Gateway Fabric, Cilium) рассматривал, но под требования кейса Envoy подходит лучше.
3. *Почему Calico, а не flannel/Cilium?* — Нужны рабочие NetworkPolicy (default-deny в `hello`); flannel их не поддерживает; Cilium — избыточно для одного узла.
4. *Почему kubeadm, а не k3s/kind?* — Требование кейса — настоящий кластер; kubeadm показывает все слои. kind подходит для CI, но не для демонстрации.
5. *Почему Kubernetes 1.36, а не 1.37?* — Версия входит в проверенную матрицу совместимости Envoy Gateway v1.9; патч зафиксирован, пакеты на `apt-mark hold`.
6. *Почему Fluentd + VictoriaLogs, а не Loki/OpenSearch?* — Fluentd указан в кейсе; VictoriaLogs принимает JSON lines по HTTP без сторонних плагинов, мало RAM. OpenSearch тяжелее, Loki требует иной модели индексации.
7. *Почему NodePort?* — Работает в любой сети без свободных IP; MetalLB не реализован, это зафиксировано в README. Для production — LB (кейс, п.1).
8. *Почему Angie?* — Указан в кейсе; встроенный `prometheus all` без sidecar-экспортёра. Запасной вариант — nginx-unprivileged + exporter (`images.nginx_fallback`).
9. *Зачем Ansible + Helm + Kustomize + Make, это не слишком?* — Каждый для своего: Ansible — хост и kubeadm, Helm — версионированные чарты, Kustomize — наши манифесты, Make — точка входа. Всё идемпотентно, и это проверяется.

**Как работает**
10. *Как реализовано 90/10?* — `HTTPRoute` с двумя `backendRefs` (веса 90 и 10) на `hello-v1`/`hello-v2`; заголовок `x-variant: v2` жёстко направляет на v2 (канареечная проверка).
11. *Как работает сквозной request_id?* — `ClientTrafficPolicy: PreserveOrGenerate` в Envoy, Angie пишет заголовок в JSON-лог и возвращает его; Fluentd кладёт поле `request_id`; поиск `make logs-find ID=…` показывает записи `gateway_access` и `access`.
12. *Как вы убедились, что всё работает?* — `make verify`: 17 проверок, реальные ответы; `make idempotency-check`: `changed=0`; CI. Выполнено на ВМ в РФ через профиль зеркал.
13. *Что происходит при недоступности VictoriaLogs?* — У Fluentd дисковый буфер до 512 МБ с `retry_forever`; потери нет, пока буфер не заполнится; алерт `LogPipelineBacklog`.
14. *Как устроена безопасность?* — PSA `restricted` в `hello`; non-root (uid 101), read-only FS, drop ALL, seccomp; default-deny NetworkPolicy (разрешены Envoy→8080, Prometheus→9113, DNS); секреты не в git, пароль Grafana генерируется при деплое.
15. *Как работает rate limit?* — `BackendTrafficPolicy`, local rate limit 100 rps → 429. **Нюанс**: локальный лимит считается на каждый экземпляр Envoy, при двух репликах суммарно до ~200 rps; для точного лимита нужен global rate limit (Redis) — следующий этап.

**Слабые места (называем сами, без оправданий)**
16. *Что если узел упадёт?* — Полный простой: один узел. Это главный пункт кейса (HA). Платформа воспроизводится из кода за ~6 мин (с кэшем), состояние (метрики/логи) на local-path и без бэкапа — потеряется.
17. *Почему `monitoring` и `logging` в privileged, а не baseline?* — node-exporter использует hostPath/hostNetwork, Fluentd читает `/var/log` узла. Осознанное, документированное исключение; в production — изолировать такие поды на отдельные узлы/policy-engine (Kyverno).
18. *Метрики control-plane на 0.0.0.0?* — Для kubeadm это нужно, чтобы Prometheus видел targets; риск закрывается firewall/NetworkPolicy и привязкой к внутреннему интерфейсу (кейс, п.3).
19. *`/__error_demo` доступен через Gateway?* — Нужен `make verify`, чтобы детерминированно породить error-лог. В production убирается или закрывается (кейс, п.3).
20. *Зеркала — это безопасно?* — Нет, без проверки подписи; включаются автоматически только при блокировках (`MIRRORS=off` вручную). В production — собственный registry с проверкой digest/подписи.
21. *Проверялся ли прогон без зеркал?* — Отдельно нет; источники загрузки те же, что до правок. Это записано в README в разделе ограничений, я не заявляю того, что не проверял.
22. *Что бы сделали иначе?* — Сразу CI с `kind` для e2e на каждый PR, GitOps вместо push-деплоя, раньше вынес бы зеркала в собственный registry.
23. *TLS самоподписанный — это проблема?* — Для стенда нет публичного домена; цепочка cert-manager (selfSigned → CA → Certificate, ECDSA P-256, автопродление) та же, что для Let's Encrypt: заменяется `ClusterIssuer`.

**ИИ**
24. *Как отличить ошибку ИИ от правды?* — Любое утверждение проверяется выполнением: запуск на чистой ВМ, `verify`, идемпотентность, CI; смотрю фактические логи, а не пересказ. Пример: роль `secrets`/namespace, которых не было.
25. *Что бы вы не стали делегировать ИИ?* — Выбор архитектуры, границ безопасности, приоритетов и приёмку результата.
