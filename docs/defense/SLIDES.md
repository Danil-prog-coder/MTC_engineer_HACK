## Слайд 2. Архитектура решения (0:50)

**Заголовок:** Одна команда — рабочая платформа

**Схема (одна картинка, 5 блоков слева направо):**
`Клиент` → `Envoy Gateway (Gateway API) :30080 / :30443` → `HTTPRoute` → `Angie hello-v1 / hello-v2 (×2 реплики)`
Снизу две линии: `метрики → Prometheus → Grafana` и `логи → Fluentd → VictoriaLogs`.

**Текст на слайде (справа от схемы):**
- `make deploy`: Ansible → kubeadm 1.36 (Calico) → Helm + Kustomize, на чистой Ubuntu 24.04
- Вход: Envoy Gateway, TLS через cert-manager, деление трафика 90/10
- Метрики: Prometheus и Grafana собирают Angie, Envoy, Fluentd, кластер
- Логи: Fluentd → VictoriaLogs, сквозной `request_id`
- `make verify`: 17 автопроверок, отчёт с реальными ответами

**Блок «Почему так» (3–4 строки под схемой):**
- kubeadm — настоящий кластер, а не имитация (kind/k3s)
- Calico — работают NetworkPolicy
- Envoy Gateway — эталонная реализация Gateway API, метрики и политики из коробки
- NodePort — работает в любой сети без свободных IP

**Речь:**
> «Решение — воспроизводимая платформа. Запрос идёт так: клиент попадает на Envoy, тот по HTTPRoute направляет его в сервис Angie. Метрики собирает Prometheus, логи уходят во VictoriaLogs. Ключевая деталь — сквозной `request_id`: Envoy создаёт его, Angie пишет в лог и возвращает клиенту, поэтому по одному идентификатору находятся записи и шлюза, и приложения. Kubeadm выбрал, потому что задача — настоящий кластер, а команда `make verify` сама доказывает, что всё работает.»

## Ответы на вопросы жюри (4 минуты)

Формула: факт → причина → ограничение. Каждый ответ 15–25 секунд.

**Выбор решений**
1. **Почему Gateway API, а не Ingress?** Типизированная модель с разделением ролей; веса, заголовки, редиректы и политики без аннотаций. Ingress больше не развивается как основной способ. `[ПРОВЕРЬ формулировку]`
2. **Почему Envoy Gateway?** Эталонная реализация, метрики и политики Envoy из коробки. Альтернативы (NGINX Gateway Fabric, Cilium) рассматривал; для кейса Envoy подошёл лучше.
3. **Почему Calico?** Нужны NetworkPolicy (default-deny в `hello`); flannel их не умеет; Cilium избыточен для одного узла.
4. **Почему kubeadm, а не k3s/kind?** Нужен настоящий кластер; kind пригоден для CI, но не для демонстрации всех слоёв.
5. **Почему 1.36, а не 1.37?** 1.36 входит в проверенную матрицу Envoy Gateway v1.9; патч зафиксирован, пакеты на `apt-mark hold`.
6. **Почему Fluentd + VictoriaLogs?** Fluentd указан в кейсе; VictoriaLogs принимает JSON lines по HTTP без сторонних плагинов, лёгкий. OpenSearch тяжелее.
7. **Почему NodePort?** Работает в любой сети без свободных IP. Это ограничение, закрывается в п.1 кейса.
8. **Почему Angie?** Указан в кейсе, встроенный `prometheus all`; запасной вариант — nginx-unprivileged с exporter.
9. **Не слишком ли много инструментов?** Каждый для своего: Ansible — хост и kubeadm, Helm — версионированные чарты, Kustomize — наши манифесты, Make — вход. Всё идемпотентно, это проверяется.

**Как работает**
10. **Как реализовано 90/10?** `HTTPRoute` с двумя `backendRefs` и весами 90 и 10; заголовок `x-variant: v2` направляет строго на v2.
11. **Как работает request_id?** `ClientTrafficPolicy: PreserveOrGenerate`; Angie пишет заголовок в JSON-лог и возвращает его; Fluentd сохраняет поле; `make logs-find ID=…` находит `gateway_access` и `access`.
12. **Как вы убедились, что всё работает?** `make verify` (17 проверок), `make idempotency-check` (`changed=0`), CI. Выполнено на ВМ в РФ через профиль зеркал.
13. **Что если VictoriaLogs недоступна?** Дисковый буфер Fluentd до 512 МБ, `retry_forever`; алерт `LogPipelineBacklog`.
14. **Безопасность?** PSA `restricted`, non-root, read-only FS, drop ALL, seccomp, default-deny NetworkPolicy, секреты не в git, пароль Grafana генерируется при деплое.
15. **Rate limit?** Local rate limit 100 rps → 429 на каждый экземпляр Envoy, при двух репликах суммарно до ~200 rps; для точного лимита нужен global rate limit.

**Слабые места (называем сами)**
16. **Что если узел упадёт?** Полный простой: один узел. Платформа воспроизводится из кода за ~6 минут, но метрики и логи на local-path пропадут. Это пункт 1 кейса.
17. **Почему `monitoring` и `logging` в privileged?** node-exporter требует hostPath/hostNetwork, Fluentd читает `/var/log` узла. Осознанное, документированное исключение; в production изолируют отдельными узлами и policy-engine.
18. **Метрики control-plane на 0.0.0.0?** Нужно kubeadm для targets Prometheus; закрывается файрволом (п.3 кейса).
19. **`/__error_demo` через Gateway?** Нужен `make verify` для детерминированного error-лога; в production убирается (п.3).
20. **Зеркала безопасны?** Нет, подпись не проверяется; включаются при блокировках, вручную `MIRRORS=off`. Для production — свой registry.
21. **Проверялся ли прогон без зеркал?** Отдельно нет; это прямо указано в README. Не заявляю того, что не проверял.
22. **Что сделали бы иначе?** Раньше добавил бы e2e в CI на kind, GitOps вместо push-деплоя и собственный registry.
23. **Самоподписанный TLS?** Публичного домена нет; цепочка cert-manager (selfSigned → CA → Certificate, ECDSA P-256, автопродление) та же, что для Let's Encrypt — меняется `ClusterIssuer`.

**ИИ**
24. **Как отличаете ошибку ИИ?** Любое утверждение проверяется выполнением: чистая ВМ, `verify`, идемпотентность, CI; смотрю логи, а не пересказ. Пример — несуществующая роль `secrets`.
25. **Что не делегировали бы ИИ?** Архитектуру, границы безопасности, приоритеты и приёмку результата.
