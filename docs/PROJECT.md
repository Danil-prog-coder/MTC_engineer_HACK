# О проекте: что, зачем и как мы делали

Короткий рассказ о проекте для тех, кто видит репозиторий впервые. Техническая инструкция (установка,
проверки, ограничения) — в [README](../README.md), устройство системы — в [architecture.md](architecture.md).

## Что это

**Hello Platform** — решение кейса «DevOps» хакатона MTC ENGINEER HACK. Это инфраструктура как код:
на чистом сервере с Ubuntu 24.04 одна команда `make deploy` разворачивает готовую мини-платформу.

| Слой | Что получаем |
|---|---|
| Кластер | Kubernetes 1.36, созданный через kubeadm (один узел, сеть Calico) |
| Приложение | веб-сервер Angie, отвечает `Hello World!`; две версии (`v1`/`v2`) по две реплики |
| Вход трафика | Gateway API на Envoy Gateway: HTTP на порту 30080, HTTPS на 30443 |
| Мониторинг | Prometheus, Alertmanager, Grafana с готовыми дашбордами и алертами |
| Логи | Fluentd собирает логи всех контейнеров и отправляет их в VictoriaLogs |
| Проверка | `make verify` сам прогоняет все проверки и пишет отчёт `artifacts/verification-report.md` |

Удаление тоже одной командой: `make destroy CONFIRM=yes`.

## Зачем

По кейсу нужно было поднять на голой машине Kubernetes, опубликовать приложение через Gateway API,
подключить мониторинг и сбор логов и показать, что всё это работает. Мы поставили себе требования
жёстче, чем «один раз запустилось у нас»:

1. **Одна команда, без ручных правок.** Проверяющий клонирует репозиторий и запускает `make deploy`.
   IP узла определяется сам, редактировать манифесты не нужно.
2. **Воспроизводимость.** Все версии записаны в одном файле [`versions.yaml`](../versions.yaml), тегов
   `latest` нет, пакеты Kubernetes закреплены через `apt-mark hold`. Через месяц развернётся то же самое.
3. **Доказательство вместо слов.** Мы не утверждаем «мониторинг работает», а показываем это: `make verify`
   по каждому требованию кейса выполняет реальный запрос (curl, PromQL, поиск в логах) и кладёт в отчёт
   команду для ручной проверки и полученный ответ.
4. **Повторный запуск ничего не ломает.** `make deploy` можно запускать сколько угодно раз. Второй прогон
   ничего не меняет (`changed=0`), и это тоже проверяется автоматически: `make idempotency-check`.
5. **Без секретов в git.** Пароль Grafana генерируется при установке и хранится только на сервере.

## Как устроено

```
make deploy
  └─ bootstrap: виртуальное окружение Python с Ansible и нашей утилитой hackops
  └─ ansible-playbook site.yml
       хост:        проверки (preflight), подготовка ОС, containerd, kubeadm/kubelet/kubectl, Helm
       кластер:     kubeadm init, сеть Calico, хранилище local-path
       платформа:   namespace и секреты, cert-manager, Envoy Gateway, Prometheus-стек, Fluentd + VictoriaLogs
       приложение:  Angie hello-v1/v2, маршруты HTTPRoute
       финал:       ждём готовности всех компонентов и HTTP 200 через Gateway
make verify  →  hackops verify  →  отчёт со статусами PASS/FAIL
```

Путь запроса: клиент → Envoy (NodePort 30080/30443, здесь же завершается TLS) → `HTTPRoute` → Service →
Angie. Envoy присваивает запросу `X-Request-Id`, приложение пишет его в свой лог и возвращает в ответе.
Поэтому один запрос можно найти в логах и шлюза, и приложения: `make logs-find ID=...`.

### Почему выбрали именно эти инструменты

| Решение | Почему |
|---|---|
| kubeadm, а не kind или k3s | В кейсе приоритет на «настоящий» кластер |
| Kubernetes 1.36 | Входит в диапазон версий, поддерживаемых Envoy Gateway v1.9; 1.37 в него не входит |
| Envoy Gateway | Эталонная реализация Gateway API; метрики, rate limit и ретраи есть из коробки |
| Angie | Назван в кейсе; умеет отдавать метрики Prometheus без отдельного экспортёра |
| Calico | С ним работают NetworkPolicy (у flannel их нет) |
| Fluentd → VictoriaLogs | Отправка по HTTP без сторонних плагинов, мало памяти; Loki и OpenSearch тяжелее |
| Ansible + Helm + Kustomize + Make | Модули Ansible честно сообщают, изменилось ли что-то. С `kubectl apply` из shell идемпотентность не доказать |
| NodePort вместо LoadBalancer | Работает в любой сети без выделенных IP-адресов |

Сверх обязательной части сделаны: HTTPS через cert-manager и редирект HTTP → HTTPS, разделение трафика
90/10 между версиями и выбор версии по заголовку `x-variant`, rate limit (100 rps) и ретраи, сквозной
`request_id`, NetworkPolicy и Pod Security `restricted` для приложения, дашборды Grafana и CI в GitHub Actions.

## Как мы это делали

Проект собран примерно за неделю (30 сентября — 4 октября 2026). Код писали вместе с ИИ-ассистентом
Claude Code: часть изменений пришла через pull request'ы из его веток, остальное — коммиты автора.
Работали итерациями «написали → прогнали на живой ВМ → починили по логам».

**1. Каркас (30 сентября).** Структура репозитория: Ansible-роли, Kustomize-манифесты, values для
Helm-чартов, Python-утилита `hackops` с командой `verify`, `Makefile` как единая точка входа. Сразу
записали все версии в `versions.yaml`. Версии, которые не удалось проверить по документации, пометили `(verify)`
и составили чек-лист для проверки на реальной машине ([VERIFY_ON_VM.md](VERIFY_ON_VM.md)).

**2. Доводка на живой ВМ (1–2 октября).** Первые прогоны на чистой Ubuntu 24.04 нашли проблемы, которых
на бумаге не видно:

- Helm-релиз CRD Envoy Gateway не помещался в Secret Kubernetes (лимит 1 МиБ). Перешли на
  `helm template` и server-side apply.
- Старый apt-репозиторий Helm устарел, бинарник теперь скачивается с `get.helm.sh` с проверкой sha256.
- Модули Ansible для Kubernetes не могли читать `admin.conf` без root, поэтому создаём kubeconfig пользователя.
- Fluentd терял error-логи Angie, если строка была не в JSON. Исправили, заодно вынесли его состояние
  из read-only `/var/log`.
- Метрики Angie не отдавались, пока не подключили шаблон `prometheus all`.
- Сеть оказалась главным врагом: таймауты при скачивании Helm-индексов, образов и apt-пакетов.
  Добавили повторы во все сетевые задачи, предзагрузку образов control-plane перед `kubeadm init`
  и откат (`kubeadm reset`), если инициализация упала, чтобы повторный запуск шёл с чистого листа.

**3. Бонусы (2 октября).** Только после зелёных `make deploy && make verify` добавили TLS, редирект,
rate limit, дашборды Grafana, алерты и CI. Правило было простое: в README попадает только то,
что можно проверить командой.

**4. Сеть с блокировками (4 октября).** Тестовая ВМ стояла в РФ, и с неё нестабильно открывались
PyPI, Docker Hub, quay.io и CDN Kubernetes. Сделали профиль зеркал [`mirrors-ru.env`](../mirrors-ru.env)
(pip, apt-репозиторий Kubernetes, зеркала реестров для containerd) и запасные пути: если недоступен
`get.helm.sh`, helm берётся из образа той же версии; если недоступен Ansible Galaxy, коллекции ставятся
из пакета `ansible` с PyPI. Чарты и манифесты кэшируются в `/var/cache/hackops`, поэтому повторный деплой
после `destroy` идёт около 6 минут вместо часа. Все известные сетевые нюансы собраны в README, раздел 7.

### Результат

На ВМ Ubuntu 24.04 (2 vCPU / 8 ГБ, РФ, с профилем зеркал) пройден полный цикл
`destroy → deploy → verify → idempotency-check → verify`: **17 из 17 проверок PASS**, повторный прогон
`changed=0`, 31 под в состоянии Ready, кластер сам поднимается после перезагрузки ВМ.

### Что осталось

- Полный прогон без зеркал на машине с обычным интернетом пока не выполнялся.
- Один узел, без отказоустойчивости. Worker-узлы добавляются только вручную.
- Доступ через NodePort, MetalLB не реализован. Сертификат самоподписанный.
- Grafana, Prometheus и интерфейс логов доступны только через `kubectl port-forward`.

Полный список ограничений — в [README, раздел 15](../README.md#15-известные-ограничения).
